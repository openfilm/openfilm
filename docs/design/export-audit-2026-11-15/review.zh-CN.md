# 导出体积与速度审查 · 2026-11-15

审查结论：T12 的 5.2G 主要来自整页无损 PNG 视频，当前“页面出现过透明像素，就整段用 PNG”的决策放大了体积。应先减少重复编码、重复帧和无效画布，再调整透明素材的表示方式。降低分辨率、帧率或强制码率上限，不符合本次保画质的要求。

此文保留首轮调查和副本实验的记录。后续实现、整片冷/热缓存实测及剪映验收，见 [实现与整片实测](./implementation.zh-CN.md)。

## 实物拆解

本机找到与截图同名的「社区体检T12」草稿及原始 film.html，未修改它们。草稿共 80 个文件，5,585,786,936 bytes，即 **5.586 GB / 5.202 GiB**，与截图的 5.2G 对得上。素材原始时间约 134.25 秒，导出按 30 fps 对齐。

| 内容 | 实际体积 | 观察 |
| --- | ---: | --- |
| 25 个页面 p01–p25 | 4,929.37 MB | 全部是 1080×1920 RGBA PNG 编码的 MOV。 |
| 两段圆形口播 PiP | 546.99 MB | PNG 视频，带自己的 PCM 音轨；内容只占画布的一小块。 |
| 三段全屏口播 | 92.68 MB | H.264 视频并带 PCM 声音。 |
| 字幕备用渲染层 | 2.55 MB | 134.27 秒只有 83 个存储帧，已经有效去重。 |
| 头像、封面、工程数据等 | 约 14.20 MB | 不是主要体积来源。 |

`p02.mov`：5.1 秒、153 帧、595.84 MB。`p16.mov`：7.73 秒、232 帧、583.78 MB。二者都不是 ProRes，也不是低效的最终 MP4；它们是供剪映合成的无损 PNG 图层。

## 四项关键发现

**1. 83 帧的透明片头，让 18 页后续 2961 帧不透明画面继续使用 PNG。**

逐帧解码检查 25 页的 alpha 最小值，18 页均是开头 3–8 帧透明、后面 alpha 全为 255；这 18 页合计仅 83 帧透明，2961 帧不透明。后者当前占用 **3,427,810,629 bytes**，相当于整个草稿的 61.4%。这是待优化的数据量，不是已经实现的净节省。

对应本地 `exports.mjs` 的 `asEditorsPlay`/`page`，以及 `render.mjs` 的 `clearFormat`/`encodeWatching`；远端也采用同一整段回退规则。T12 共用 `kit.js` 的入场平移/缩放在页面边缘露出透明，正好触发回退。另 7 个页面确实持续透明，不能直接补实色背景。

**2. 去重有 50% 门槛，而且所有透明 PNG 都再编码一次。**

`keepChanges()` 已经计算相邻包哈希，但 `kept.length > sums.length / 2` 时不执行 select，完全重复的帧也留下。无论有无重复，又都经过 PNG 解码和默认参数重新压缩。

29 个 PNG 视频共有 7215 个存储帧；按相邻包完全一致、保留首末帧的规则，可以少存 890 个包，合计 **403.83 MB**（草稿约 7.2%，未计算容器微小差异）。这是保守的潜力估算，音轨仍需原样保留。

在 p02 副本中，用 `noise` bitstream filter 明确设置 `amount=0`，仅移除已确认重复的 PNG 包并保留 PTS，153 个存储帧变成 125 个：**595.84 → 483.81 MB，减少 18.8%**。按 30 fps 还原后，153 帧的 RGBA 哈希及时间戳全部相同。

当前 `keepChanges` 在该副本上约 14.03 秒，得到的仍为 595.84 MB；扫描加包级去重约 1.39 秒。只说明该后处理步骤的差异，不能外推成整片十倍提速。[FFmpeg 文档](https://ffmpeg.org/ffmpeg-bitstream-filters.html#noise)明确说明 bitstream filter 不需要解码；使用 `noise` 时必须显式禁止字节修改，不能省略相关设置。

**3. 小画中画按整张画布截图和编码。**

对 a-pip-1 全部 1896 帧扫描，包含所有非零 alpha 和阴影的联合包围盒为 **x=654、y=68、424×424**，只有全画布面积的 8.7%。

前 60 帧试验：整帧 PNG 编码约 1.43 秒 / 10.59 MB，裁到包围盒约 0.76 秒 / 9.25 MB。补回原画布后，这 60 帧 RGBA 及时间戳完全一致。计时文件包含默认重编码的音轨，故此项只作为视频裁剪方向的初测，不作为完整导出基准；正式实现必须映射并复制原音轨。

空透明区域本来就很容易压缩，因此不能把“少处理 91.3% 像素”误报为“文件减小 91.3%”。要显著降低截图成本，还需让浏览器直接截取安全区域，而不是截图后才 crop。联合边界需覆盖整段的位移、模糊和阴影，并在剪映中补偿素材尺寸与位置。

**4. 换一个编码器或调高 PNG 压缩级别，不足以同时保画质、减容和提速。**

| 副本实验 | 大小 / 时间 | 结论 |
| --- | --- | --- |
| p02 前 30 帧，默认 PNG | 125.64 MB / 6.06 s | 基线。 |
| 同帧，PNG sub + level 1 | 129.18 MB / 1.05 s | 逐帧 RGBA 相同；约多 2.8% 字节，但编码明显更快。 |
| 同帧，PNG mixed + level 6 | 122.06 MB / 6.55 s | 逐帧 RGBA 相同；只比默认小约 2.8%，不解决量级问题。 |
| p16 去掉透明片头，H.264 CRF14 slow | 8.69 MB / 13.89 s | VMAF 均值约 97.00，不能声称没有画质变化。 |
| 同一段，H.264 CRF8 slow + grain | 32.87 MB / 23.43 s | VMAF 均值约 97.75、最低约 97.03；更低 CRF 仍不是逐像素无损。 |
| p16 全段，lossless QTRLE | 1150.55 MB / 3.49 s | 比原 PNG 还大；未验证剪映兼容性，不能当作解决方案。 |

VMAF 参考帧先按相同 BT.709 路径转为 4:2:0；这些分数不能覆盖 RGB→YUV 的全部损失，更不能验证透明边缘和剪映实际合成。所有计时都是单次本机局部实验，部分实验存在并行负载。

T12 存在设计使用的噪点、半透明渐变、图像微动和持续变化的 HUD。这些内容不能为了压缩被静态化、降帧或抹掉。需要减少的是重复保存它们的方式。

## 建议实施顺序

**P0：先落可证明像素不变的改动，并建立可观测的基准。**

1. 去掉去重的 50% 门槛；对 PNG 做包级精确去重，保持 VFR 的原 PTS、首末帧和持续时间。音轨独立复制。小到只有一个像素/一个 alpha 色阶的变化也必须保留。
2. 删除透明素材固定的第二次 PNG 编码；从浏览器 PNG 到 MOV 的直封装另做兼容性验证。存在缩放、运动模糊、像素格式或颜色变换时仍走必要处理。当前 quick PNG 体积略大与二次压缩的成本，需要用真实素材选择策略，而非一律重压。
3. 加安全包围盒和导出素材位置补偿，先覆盖静态圆形 PiP、贴纸、字幕；无法证明边界时保持原画布。避免在最后一帧才发现裁掉阴影。
4. 记录每个素材的绘制、截图、PNG 解码/编码、去重、音频、封装耗时，记录 CPU/GPU/内存、输入输出字节和缓存命中。先区分 CPU、GPU、磁盘和截图瓶颈，再决定并发。

**P1：解决 3.43GB 的错误编码范围，采用经过验收的质量策略。**

1. 将单个 `clear` 布尔值升级为按帧的透明区间。在一次绘制中识别并写出连续区间，透明段保留 PNG，不透明段可以选择经过验证的编辑编码；避免透明出现在末尾就把前面全部重画。
2. 优先把能准确表达的定位、裁切、矩形/圆形蒙版、透明度、变速和淡入淡出写成剪映原生控制，复用源视频/图片。延续 #450，按能力逐项验证，不能用近似效果替换任意 CSS。
3. 页面入场与主体可分离时，优先保存原内容并用目标编辑器的变换表示入场。否则拆成透明片头和主体素材；保持原时间线分组或复合关系，避免用户面对大量难以联动的小片段。
4. RGB+独立 alpha、HEVC alpha、ProRes 等方案都要先做剪映/CapCut、macOS/Windows、版本与导出回读矩阵。不能根据 FFmpeg 能编码就认定剪映能无误合成。严格逐像素模式继续有 PNG 回退。

本地未提交代码还引入了 `chipDelivery.ceiling` 和 `render.mjs` 超大小后再有损编码的路径。这有助于限制文件，但可能损伤细纹理并增加一遍编码；应明确归属体积优先的交付模式，不能把它算作“质量固定”的通用优化。

**P2：让重复导出和长片持续受益。**

1. 按页面内容、递归依赖、字体、素材内容、浏览器/渲染版本、画幅、帧率、采样、颜色与编码设置生成稳定缓存键。修改一页只重做受影响产物；与 #309 的失败续渲分开设计。
2. 对静态背景、原视频、动态叠加建立有严格适用条件的渲染计划。对普通自定义 HTML 保留浏览器回退，避免用启发式假定它不再变化。
3. 绘制、编码、去重共享资源预算，限制后台重编码任务数。当前浏览器槽位在后处理前释放，盲目扩大 worker 数会叠加 PNG 编码负载。
4. 预估拆成最终工程体积、附带源素材、临时峰值、缓存占用。链接/复制只改变素材存放与携带方式，不能消灭必需的渲染媒体，也不能用清掉历史冒充最终工程减容。

## 画质与正确性验收

第一批无损改动以逐帧、原时间网格的 RGBA 比较为门槛：时间戳、总时长和每一个可见像素一致；透明区域还需黑底、白底、棋盘底合成检查。裁剪先在 FFmpeg 恢复原画布比较，再到剪映中验证尺寸、缩放、坐标、阴影和边缘。

新的有损编码策略必须明确标识为视觉质量策略，不能称为无损。VMAF/SSIM 只作辅助，还需细字、饱和色边缘、暗部渐变、静态/动态颗粒、半透明阴影和真实口播的局部对照。不能用固定 RGB 提亮掩盖读回色彩转换问题；沿用 #366/#396 的准确舍入与颜色检查。

同时检查音画同步、声道/响度、重复帧节奏、变速、淡入淡出、隐藏轨、字幕、素材可编辑性、取消/崩溃后的清理和恢复。跨平台使用相同最小工程与目标编辑器回读；FFmpeg 校验通过不等于编辑器验收通过。

整片目标应在落地 P0 后复测 T12 再设定：报告最终字节、导出总时间及各阶段时间、磁盘临时峰值、再次导出命中率，所有结果都附画质与编辑器验收。当前证据足以安排优化优先级，尚不足以承诺整片压到某个 MB 或固定提速倍数。
