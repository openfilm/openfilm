# 剩余体积与第二阶段无损减容实验

重新拆解已验收的 2.937 GB 工程后，主要剩余问题是持续透明的整页 PNG 和圆形口播 PNG。新的存储原型已验证这些像素并不必然需要这么大的空间；剪映接入仍需另行实现和验收。

## 最终工程还存了什么

按实际媒体文件归类，媒体总量为 2,936,119,159 bytes，另有少量工程记录：

| 类别 | MB（十进制） | 媒体占比 |
| --- | ---: | ---: |
| p01/p02/p03/p15/p22/p23/p24，7 个持续透明页面 | 1310.90 | 44.65% |
| a-pip-1/a-pip-2，已裁到 424×424 的 PNG＋PCM | 474.02 | 16.14% |
| 18 页的不透明主体，无损 RGB H.264 | 713.75 | 24.31% |
| 完整原口播和头像视频 | 211.37 | 7.20% |
| 透明片头、头像、字幕、封面等 PNG | 80.63 | 2.75% |
| 3 段全屏口播 H.264＋PCM | 92.68 | 3.16% |
| 独立声音、单帧封面等 | 52.77 | 1.80% |

因此，PNG 所在的媒体文件仍约 1.866 GB（PiP 文件含 PCM），占约 63.5%。字幕视频已经只有 1.56 MB，不是下一阶段的主要对象。

最突出的是 **p02：5.1 秒，125 个存储 PNG 包，482.61 MB**。即使大部分画面没变，只要帧内一个小区域变化，现有表示仍要存另一张完整的 PNG；此前的精确去重只能移除整帧完全相同的情况。

## 透明与噪点为什么昂贵

1080×1920 的 8-bit RGBA 原始帧有 8,294,400 bytes。当前 MOV 中逐帧 PNG 是独立图片压缩，不利用相邻视频帧大面积相同的内容。PNG 的 Deflate 本身使用至多 32 KiB 的滑动窗口，和有跨帧预测的视频编码不是同一种重复利用机制。[W3C PNG 规范](https://www.w3.org/TR/png-3/)

对每页 **t=1 秒的一帧**检查 alpha：p01/p02/p03/p15/p22/p23/p24 的半透明像素比例分别约为 **94.9%、95.5%、99.5%、80.3%、79.6%、95.7%、80.2%**；这些采样帧没有完全透明像素。它们不能直接去掉 alpha，也不能靠裁掉外围空白解决。

源工程 `pages/lib/base.css` 的 `.grain` 使用全画布 SVG `feTurbulence`，配合 `mix-blend-mode: overlay`；主题的 `--grain` 是 0.10。渐变遮罩和这层静态噪点，使高频颜色与透明信息遍布画布。设计中的质感应保留，但没有必要在每个改变了小块文字的完整 PNG 中反复保存它。

## 已完成的新实验：颜色与透明度分开无损压缩

把每个透明媒体分成：

- RGB：`libx264rgb`、CRF 0、medium；保留 RGB 8-bit 样本。
- Alpha：原始 alpha 提取为 8-bit 灰度，`libx264` QP 0；利用透明度在相邻帧中的重复。
- 口播 PCM 音轨直接复制到 RGB 文件。
- 在 FFmpeg 中将两路重新合并为 RGBA，在原 30 fps 网格上比较完整解码字节流 SHA256。

libx264rgb 接受 RGB 输入，避免为了编码而先把颜色转成有损的 YUV 4:2:0；其能力见 [FFmpeg 文档](https://ffmpeg.org/ffmpeg-codecs.html)。这里是否无损以实际完整字节流校验为准，不只依据编码器参数名称。

| 完整媒体 | 现有文件 MB | RGB＋Alpha 原型 MB | 节省 |
| --- | ---: | ---: | ---: |
| p01，163 帧 | 169.80 | 14.89 | 91.2% |
| p02，153 帧 | 482.61 | 21.99 | 95.4% |
| p03，140 帧 | 120.09 | 16.23 | 86.5% |
| p15，181 帧 | 199.96 | 31.03 | 84.5% |
| p22，156 帧 | 166.46 | 32.35 | 80.6% |
| p23，160 帧 | 114.17 | 11.61 | 89.8% |
| p24，91 帧 | 57.82 | 9.07 | 84.3% |
| a-pip-1，1896 帧，含原 PCM | 301.18 | 144.83 | 51.9% |
| a-pip-2，1088 帧，含原 PCM | 172.84 | 82.92 | 52.0% |
| **合计，4028 个图层帧** | **1784.92** | **364.92** | **79.6%** |

全部 9 项的 RGBA 完整字节流 SHA256 一致；两段随片 PCM 的解码 SHA256 也一致。没有降低尺寸、帧率、RGB 或 alpha 位深。

**这是存储和重建原型，尚未接入剪映。** 当前导出器没有把两个独立编码流映射为剪映单个透明素材的合成路径。不能直接将它们当成两条普通视频轨就认为透明度正确。需要实现并回读验证蒙版映射、颜色/透明度范围、straight/premultiplied alpha 与两路帧同步。

若剪映可以直接消费这个表示，其余文件完全不变时，静态算术推算为：

`2,936,610,530 − 1,784,924,322 + 364,915,320 = 1,516,601,528 bytes`

约 **1.52 GB**。**这不是已经能使用的剪映草稿大小，也不是交付承诺。** 如果进入剪映前又把它恢复成全尺寸 PNG 视频，剪映工作目录依然会变大，得到的只是传输包减容。

## 建议的实现顺序

1. **原片复用与原生控制。** 优先处理圆形 PiP：复用已经随工程携带的原视频，圆形裁切由剪映原生蒙版表达，固定边框/阴影单独保存成小图片。3 段全屏口播也应检查能否用原片＋原生裁切替代再次烘焙。圆边、阴影、位置、色彩和声音需要真实合成回读；当前文件大小代表处理对象，不能全部计作净节省。
2. **透明视频的帧间无损表示。** 对上面 7 个页面验证双通道透明合成，或者验证能够承载 RGB 与 alpha 帧间无损压缩、且目标编辑器实际支持的单文件格式。上述完整原型给出了这一路线的实际压缩空间。
3. **静态与动态内容分离。** 背景图、固定文字、阴影、网格和噪点纹理保留为可复用的静态资源；推镜、位置与透明度由原生变换表达；真正需要浏览器绘制的动态区域才写视频。文本可保留为 PNG 字形图层以保留外观。必须保持混合模式、渐变与采样结果，不通过取消噪点来减容。
4. **空间划分作为回退。** 对静态区域多、少数区域变化的页面，验证非重叠区域/图块的独立存储和精准位置补偿。须控制文件数量、相邻区域的边缘采样以及整体编辑能力；不能直接把几百块散到用户时间线。
5. **引用原片可选。** 不复制完整原片可让导出目录减少约 211 MB，画面数据不变，但总项目存储没有因此消失，且会引入路径依赖。它不能单独解决 1.866 GB 的 PNG 媒体问题。

整体方向是源视频复用、静态资源复用和透明数据的帧间压缩。缓存已能明显缩短再次导出时间，但不减少单个草稿的必需媒体大小。

## 不优先采用的参数替换

同一段 p16 无损 RGB 的前 60 帧：

| 编码方式 | MB | 编码时间 | RGBA 一致 |
| --- | ---: | ---: | --- |
| x264rgb veryfast，CRF 0 | 63.30 | 2.34 s | 是 |
| x264rgb medium，CRF 0 | 62.78 | 4.47 s | 是 |
| x264rgb slow，CRF 0 | 62.68 | 5.36 s | 是 |
| x265 RGB lossless，medium | 62.52 | 36.56 s | 是，剪映未验证 |

本样本中更慢的 x264 只节省约 1%，RGB 无损 HEVC 也只节省约 1.2%。这些单次局部计时不是整片性能结果，不能外推所有视频，但足以说明不应把本片的主要希望押在换 preset 上。

ProRes 4444 的 RGB/YCbCr 属于视觉无损，数学无损保证针对 alpha；不能直接把它作为严格逐像素无损的同义词，而且其数据率并不低。[Apple 官方说明](https://support.apple.com/en-us/102207)

本轮只分析并对副本做原型实验，未修改已经验收的剪映草稿或正式导出实现。完整数据见 [第二阶段实验数据](./further-evidence.json)；本机实验脚本和两路媒体在 `/tmp/openfilm-export-perf-20261115/further/`。
